The context gap

Source code is exact. It is not organized for agent reasoning.

SwiftUI architecture is spread across wrappers, initializers, closures, modifiers, and files. An agent needs the relationships between them, not a larger pile of source text.

01

Ownership is distributed

One value can appear as State, Binding, an observed member, a callback parameter, and a derived representation.

02

Effects hide behind value syntax

Lifecycle hooks, custom setters, and reciprocal copies can form an imperative system underneath body.

03

Text diffs miss semantic movement

A line diff can show an edit without showing whether ownership, write authority, or a transaction boundary changed.

Semantic twin

Keep the data flow. Drop the syntax noise.

The twin is a compact, versioned representation built by the CLI. It is smaller than source, but every supported fact stays tied to evidence and confidence.

Inside the semantic twin

A smaller model of the program, not a summary of the code.

This editorial X-ray shows fixture-backed ownership and copy paths from the semantic graph. It is not a product GUI, an LLM summary, or model-written pseudocode.

Manual synchronization

BindingMirroredLocally two owners 
struct BindingMirrorEditor: View {
    @Binding var profileName: String
    @State private var editableName = ""

    var body: some View {
        TextField("Name", text: $editableName)
            .onAppear { editableName = profileName }
            .onChange(of: profileName) {
                editableName = profileName
            }
            .onChange(of: editableName) {
                profileName = editableName
            }
    }
}

Reading the twin

One value has two mutable representations and reciprocal copy paths.
  1. OwnerprofileName is borrowed from the parent.
  2. OwnereditableName is local State.
  3. CopyonAppear seeds the local value.
  4. BindTextField writes to the local value.
  5. SyncEach representation copies into the other.

Direct Binding

GoodDirectBinding one owner 
struct DirectBindingField: View {
    @Binding var name: String

    var body: some View {
        TextField("Name", text: $name)
    }
}
No mirror finding is expected. The parent remains the owner and the field receives direct write authority.

Protected case

A real local draft is not a fix target.

A draft is valid when the UI has real commit and discard behavior. The distinction comes from action and copy topology, not button names.

Representative protected transaction no finding expected 
@Binding var name: String
@State private var draft = ""

func applyEdits() { name = draft }
func abandonEdits() { draft = name }

TextField("Name", text: $draft)
Button("Apply") { applyEdits() }
Button("Discard") { abandonEdits() }
  • Separate lifetimeThe draft remains local until commit.
  • Explicit commitApply writes to the external owner.
  • Explicit rollbackDiscard restores the owned value.
  • No mechanical fixThe valid transaction stays intact.

Release 0.5.0 agent loop

Build the twin, gate the evidence, then edit.

The released workflow is exact-state and on demand. Each agent run validates the compiler evidence it consumes; it does not rely on a background watcher receipt.

  1. 1

    Build the exact state

    Produce a project-covering raw Index Store for the source under review.

  2. 2

    Compile the twin

    Extract syntax and compiler facts into one canonical semantic graph.

  3. 3

    Gate the result

    Require indexed resolution and the expected configuration identity.

  4. 4

    Slice one concern

    Send the agent the ownership and data-flow path needed for the task.

  5. 5

    Judge and edit

    The agent establishes intent, then makes the smallest supported change.

  6. 6

    Compare and test

    Review the semantic delta alongside builds, behavior tests, and source.

Fail closed. Missing coverage, invalid JSON, syntax-only fallback, mixed resolution, or a configuration mismatch is a blocker—not an empty or clean result.

Trust and limits

Know what the twin proves—and what it does not.

The CLI compiles deterministic facts. Skills route bounded evidence to Codex or Claude; the agent supplies contextual judgment.

Released and inspectable

Source, immutable 0.5.0 tag, archive, and MIT license are public.

No automatic rewriting

The CLI reports evidence. It never edits project source.

LLM is not the extractor

Each extraction's source, symbol, read/write, and location facts are deterministic; agent judgment stays separate.

No embedded model API

The CLI is provider independent; the agent host controls its own data handling.

The bounded twin is not a full type checker, runtime simulator, control-flow engine, security audit, or performance profiler. A clean report or semantic diff does not prove behavior.

FAQ

Using the semantic twin safely

Read the documentation
Is the semantic twin an LLM summary?

No. It is a deterministic graph compiled from supported source and compiler-index facts. The agent receives bounded slices and may infer intent, but it cannot alter the extracted records in place; a source edit produces a new extraction.

Is this a linter?

No. The CLI maps supported ownership and data-flow topology. Findings are evidence for review, not style scores or wrapper prescriptions.

Does release 0.5.0 maintain the twin continuously?

No. Release 0.5.0 builds an exact-state twin on demand. The project watcher on master is an unreleased 0.6.0 candidate.

Which skill should I use?

Use swiftui-semantic. Describe the SwiftUI outcome; the skill selects audit, refactor, or review and carries the twin evidence forward.

Does it change project source?

No. The CLI is non-mutating. A coding agent may propose a focused refactor after establishing ownership and behavior, but the tool itself never rewrites code.

Why does the agent workflow require a fresh Index Store?

Compiler-backed symbol identity and cross-file relations provide the evidence level required by the bundled workflows. They stop rather than present weaker evidence as an indexed result.

Are local drafts reported as duplicate state?

Not when the graph proves a real transaction with commit and discard behavior. Missing or fake discard topology does not receive that protection.

Does a clean semantic diff prove the refactor is correct?

No. The diff verifies supported architecture facts. Relevant builds, behavior tests, product invariants, and source review remain required.

Does the CLI send source to a model provider?

No. The CLI has no embedded model API. A surrounding agent host may read source under its own product and data policies.
